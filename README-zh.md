# dsh-token-usage

> Token 用量统计与模型能力排名 —— DeepSeek Harness 插件。

扫描 **DSH 自己写的会话日志**，按 provider 与模型归类，算出消耗趋势、缓存命中率
与各模型的用量分布；再把你**实际用过的**模型与公开能力榜单对齐，给出「用得多的
模型里哪个最强」。

| 能力 | 入口 |
| --- | --- |
| 用量主面板 | 侧栏「Token 用量」→ 主区面板（概览数字 + 四张图 + 明细表） |
| 用量 JSON | `GET {prefix}/usage`（支持 `days=` 与 `refresh=1`） |
| 模型能力排名 | 用量面板最下方（总榜 + 六类任务推荐） |
| 榜单 JSON | `GET {prefix}/model-rank`（支持 `refresh=1`） |

**这个插件不碰你的任何账号。** 它只读宿主自己的会话日志，不发起 OAuth、不复制
凭据、不注册模型 provider、不改任何客户端。

---

## 它与 `dsh-agent-checkin` 的关系

**没有关系。** 两者完全独立，可以任意单独安装：

| | `dsh-agent-checkin` | `dsh-token-usage` |
| --- | --- | --- |
| 干什么 | 每日签到、积分余额、把本机客户端接成模型 provider | Token 用量统计、模型能力排名 |
| 数据源 | 本机客户端的登录态 | 宿主自己的会话日志 |
| 会不会读对方的文件 | —— | **不会** |

历史上用量面板曾长在 `dsh-agent-checkin` 里（0.8.0 及以前）。0.9.0 之后它被拆成
独立插件：两者不共享代码、不共享缓存文件、不互相调用，装一个不影响另一个。

## 要求

- DeepSeek Harness（`dsh`）0.1.7 及以上，且组合里带有 Web 界面
- Node.js `^22.19.0 || >=24.0.0`
- 有一份可读的本机会话日志（默认位置 `$DSH_HOME/sessions`，未设 `DSH_HOME` 时用 `~/.dsh/sessions`）

---

## 安装

```bash
dsh plugin add @sole373/dsh-token-usage
```

或在 profile 的 `cordis.patch.yml` 里加一行：

```yaml
- id: dsh-token-usage
  name: '@sole373/dsh-token-usage'
```

装完重启 DSH，侧栏会出现「Token 用量」入口。

## 用法

### 用量面板

侧栏点「Token 用量」进主区。面板自上而下是：

1. **概览数字** —— 累计消耗 / 今日 / 近 7 天 / 调用次数，以及缓存命中、未命中与命中率
2. **四张图** —— 消耗趋势（柱状，可切「每日 / 累计」）、来源分布（环形）、
   模型使用排行、本机模型能力排行
3. **按来源明细** —— 每个 provider / 模型的输入、缓存读写、输出、合计、调用次数、
   命中率、均次与输出占比
4. **模型权威排名** —— 总榜 + 按任务类型（写代码 / 推理 / 智能体 / 长文档 / 多模态 /
   快而省）的推荐
5. **页脚** —— 本次扫描了多少会话文件、耗时多久、有没有扫完

时间窗可选 7 / 30 / 90 天与「全部」。点「刷新」会强制重扫文件，其余时候走缓存。

### 数字是怎么算出来的

| 指标 | 口径 |
| --- | --- |
| 单条记录的 token | `inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens` 四段分别累加 |
| 命中率的分母 | `input + cacheRead + cacheWrite`（**不含 output** —— 输出是生成出来的，不是喂进去的） |
| 命中率分母为 0 | 显示「—」，**不显示 0%**（「读不到」与「真的是 0」不是一回事） |
| 归日 | 按本机时区切天，不按 UTC |
| 「累计消耗」 | 全部历史；缓存三指标与它同基准，因此两者能对得上账 |

> **为什么不用 `totalTokens` 字段**：那个字段是旧口径，不保证与四段之和一致。
> 页面上的总量一律按四段求和。
>
> **为什么只认 `assistant/message`**：`assistant/attempt` 里也有一份 usage，
> 与最终那条是同一份；两处都数会让总量凭空翻倍。

### 增量缓存

会话日志只增不减，所以没必要每次全量重扫。扫描器记下每个文件的 `size + mtime`，
只重扫变化过的文件，其余复用上次的行级聚合结果。

- 全量冷扫：几十个日志 / 几十 MB，约 1.4 秒
- 日常刷新：命中缓存后是个位数毫秒
- 不落 SQLite：没有原生依赖、没有 schema 迁移、没有写坏的中间态

### 模型权威排名

排名分两个来源，**严格分开**：

- **能力分数** —— 公开榜单（OpenRouter 的 `/api/v1/models`，免鉴权，内含 Artificial
  Analysis 的 intelligence / coding / agentic 指数，以及上下文长度、价格、输入模态）
- **收录范围** —— 本机会话日志里**真实出现过**的模型（含已不再使用的历史调用）

所以这张榜回答的是「**我用过的这些模型里，哪个最适合干什么**」。

> ⚠️ **口径声明（写在面板上，不藏着）**：榜单只回答「这个模型的能力分数是多少」，
> **不回答「你有没有权调用它」**。收录范围来自实测调用记录，不是订阅权益检查——
> 某个模型进榜，不等于你此刻还有权调用它。

配置项 `rankScope` 改成 `all` 时，改为排公开榜单上的全部模型（世界全景），
但那时榜单里的绝大多数模型你本机并没有装。

### 榜单缓存

榜单以天为单位变化，刷太勤只是白费网络，因此缓存 6 小时（可配）。面板上的
「刷新榜单」总是绕过缓存重新拉。拉取失败**不是**致命错误：手上有旧榜单就继续
用它，并在页面上标明「本次刷新失败」。

## 配置项

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `statusRoute` | `/dsh-token-usage` | 面板 HTTP 端点前缀 |
| `sessionsDir` | `''` | 会话日志根目录；留空则用 `$DSH_HOME/sessions` |
| `usageCacheSeconds` | `30` | 用量扫描结果的缓存秒数；面板的「刷新」总是绕过它 |
| `rankCacheHours` | `6` | 榜单缓存小时数 |
| `rankScope` | `'used'` | `used` = 只排实测用过的模型；`all` = 排榜单全集 |

## 诚实报告

- **只读回环**：所有端点只接受本机回环请求。Host 不在回环一律 403；带 Origin
  时也必须是回环。挡住的是「外部页面用浏览器打本机端口」。
- **不猜**：没上榜的模型显示「—」，不显示 0 分；命中率为 0 的分母显示「—」，
  不显示 0%。「读不到」永远不长得像「读到了 0」。
- **扫描不完整会说**：扫描超时会标「本次因超时未扫完」，不会假装扫完了。
- **排行榜只有实测用过的模型**：这是「我调用过什么」，不是「世界上有什么」。

## 设计取舍

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 逐帧切分多帧 zstd | `session.v4.jsonl.zstd` 是上万个独立帧首尾相接；`zstdDecompressSync` 只解第一帧，**其余 99% 静默丢失且不报错** | 自己按魔数 `0xfd2fb528` 找帧边界 |
| 只认 `assistant/message` | `attempt` 里的 usage 与最终那条重复 | `attempt` 仅用于去重与关联 |
| 不读 `totalTokens` | 旧字段不保证与四段之和一致 | 四段分别求和 |
| 内存缓存，不引入 SQLite | 日志只增不减，内存缓存已把日常刷新压到个位数毫秒 | 宿主重启后需冷扫一次；多进程不共享 |
| 榜单用公开接口 | 能力分数必须是**别人测的**，不能自己估 | 依赖网络；离线时用旧榜单并标明 |
| 收录范围 = 实测调用 | 与能力排行卡同口径，且不依赖任何其它插件 | 榜里看不到「装了但没用过」的模型 |
